# 06 · 几个 Agent 分工，你回主帖看结果

你希望一个 Agent 完成文案，另一个核对成品。出了问题，退回具体子任务；已经通过的部分继续保留。

准备：[建立练习库](README.md#建一个独立练习库)。打开 `lab-team`，它引用两个子帖：

| 帖子 | 职责 | 可写范围 |
| --- | --- | --- |
| `lab-team-write` | 修改入门文案 | `materials/team-note.txt`、自己的子帖 |
| `lab-team-review` | 独立读取文件和复跑检查 | 自己的复核子帖；不改实现或检查器 |
| `lab-team` | 汇总、验收、退回与交接 | 主帖结果与必要的子任务反馈 |

文件初稿见 [team-note.txt](materials/team-note.txt)。两个子帖已有委托锚点，创建它们不意味着 Agent 已经开始运行。

## 先把整件事交给负责人

在 `lab-team` 下发送以下委托，并把角色替换为本机实际可用目标：

```text
@负责人 请组织本帖及两个子帖完成三行文案修订。
上下文仅限这三个帖子、materials/team-note.txt 和指定检查器。
写作方只改文案；复核方重新读取成品，独立运行检查，不替写作方改文件。

验收要求：
第一行保留“便签盒：三步开始。”
第二行改为“适用范围：macOS 已验证；其他平台待验证。”
第三行改为“操作：保存一条便签，再搜索它。”
恰好三行；运行 node examples/workflows/check-result.js team。

我授权你在可用的同一 Team 内委派上述两个角色并回收结果。
写作完成后再复核；失败最多退回写作方修正两次并复验。
超出次数、缺少可调度目标或需要扩大范围时，回主帖说明具体阻塞。
子帖写各自产物及真实证据，主帖写总结果和未决事项，等我验收。
不要把派活回执、任务板 completed 当作业务验收通过。
```

Team 的可用性取决于 DSH 宿主配置。forum-kb 提供这些工作记录，不保证你的安装已有自动团队委派或完整失败恢复。负责人应先核对可用目标和实际回执，再报告是否已启动。

## 没有 Team，也能手动跑一遍

1. 在 `lab-team-write` 下点名可用执行者，要求按子帖 query 修改文件、运行检查并回帖。
2. 写作方交付后，在 `lab-team-review` 下点名另一位可用 Agent，要求读取实现帖 current 和实际文件，独立运行同一检查，并记录所验文件 SHA-256、输出与结论。
3. 如复核失败，只在写作子帖退回具体问题；修正后重新点名复核方。每次都确认派活回执。
4. 在主帖点名负责人，汇总两个子帖的当前结果与证据，等你验收。

只有一个 Agent 时，可以用全新会话扮演复核角色，练习上下文交接；它不构成不同模型的交叉验证。共享目录写入按先实现、后复核串行进行，避免一边修改、一边验证造成证据过期。

## 验收主帖，而不只看任务板

在练习目录运行 `node examples/workflows/check-result.js team`，初始应失败，正确文件应输出 `PASS team`。复核者应独立运行，不能复制实现者的日志。若复核后文件又被修改，原 SHA-256 对应的结论就需要重验。

主帖 current 应同时说明：最终三行文字、两个子帖及 answer 引用、所验文件指纹、实际检查输出、剩余问题、是否等待你接受。子帖已提交但主帖还说“未开始”，就需要更新主帖的当前结果。

想练习一次退回，可在复核前明确委托写作方暂时把第三行留为“操作：待补充。”，保留第二行正确版本。复核应只退回第三行；修复后重验，主帖引用最新通过的结果。这个故障注入只用于练习文件，不能把失败记录写成通过。

接受后让负责人记录接受依据。文件回退恢复本次三行修改，复核与退回记录继续留在各帖中。
