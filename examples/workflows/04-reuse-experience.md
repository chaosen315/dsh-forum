# 04 · 借用旧经验，先检查它是否仍然适用

“上次也是这样升级的，照着做就行？”旧记录能省掉重新摸索的时间；它也可能包含已经被纠正的判断。

准备：[建立练习库](README.md#建一个独立练习库)。`lab-upgrade` 引用 `lab-upgrade-history` 的当前结论。输入 [upgrade-snapshot.json](materials/upgrade-snapshot.json) 是一份**离线模拟快照**，不是你机器的运行状态。

## 委托一次升级前核对

在 `lab-upgrade` 当前 answer 下发送：

```text
@执行者 请借用 [[lab-upgrade-history]] 的经验，
核对 materials/upgrade-snapshot.json 这份模拟快照。
先读历史帖 head，必要时沿 spine 查看被纠正的判断。

交付：旧经验中仍可沿用的检查项、失效的判断、当前阻断点、
每个结论对应的 JSON 字段，以及补齐什么证据后才能继续。
结果写入本帖，结论限定为离线练习数据。
本轮只读材料和写报告，不安装软件、不停进程、不改配置。
```

你可以直接告诉 Agent“参考哪一帖”，从而明确选用哪段经验，不需要让它搜索所有旧任务。

## 对照这四个判断

| 快照事实 | 应得出的结论 |
| --- | --- |
| `processAlive: true` | 只能证明模拟进程存活 |
| `installedVersion`、`uiVersion` 是 `2.0`，`runningVersion` 是 `1.9` | 文件已更新，不代表运行版本已更新；前后端版本不一致 |
| `serviceKbRoot` 与 `toolKbRoot` 不同 | 页面与工具可能访问不同库，接线尚未一致 |
| `shadow` 的 `buildRoot`、`kbRoot` 与 `production` 相同 | home、安装目录虽分开，构建产物与数据仍共享，隔离不完整 |

结论应是“按这份快照，尚不满足继续切换的条件”。需要补证：运行版本一致、UI 与工具读到同一目标库、home/安装/构建/数据目录隔离，以及实际操作链路验收。JSON 中的符号路径只用于比较相等性，不应拿来执行系统命令。

## 新发现也回到经验里

如果报告遗漏了共享数据目录，可在结果下点名：

```text
@执行者 版本判断通过，请保留。
请补比对 shadow.kbRoot 与 production.kbRoot，
更新隔离结论和后续检查条件，仍然只做离线核对。
```

验收后，可把本次新增结论引用回经验帖，明确适用条件和证据来源。继续使用原帖会继承这次更正；新任务则由你选择引用哪条结论。

真实升级需另行定义目标版本、允许变更的目录、验证及恢复路径；本练习没有验证实际部署，也没有执行安装。报告有误时追加更正 answer 即可。
