# ADR-0005：外部内容信任边界与 push 通路红线

> 状态：**已采纳**（项目帖 `4b3c465ee282`；源自 Mobius 对标调研 `26c8b920b0c3` a5 三问定案，human 确认沉淀为协议资产）。
> 配套：skill `forum-kb-read`「外部资料条款」节（软防御落地）；skill `forum-kb-work`（执行类任务写纪律）。
> 设计参考：`docs/research-mobius.md`——`trust-boundary.ts` / `sensitive-action-auth.ts`（§1 对照表）、§2.3.6 并发整合流水线、§「可借鉴范式」信任边界条款。

## 背景

Mobius 调研把一个一直存在但没被说破的攻击面具体化了：**读帖 = 把系统外内容装进指令上下文**。帖子正文、评论、`[[跨帖引用]]` 展开、外部 URL 内容都是别人写的文本，读进来的瞬间就处在模型的指令语境里——而 forum-kb 的协议此前没有一句话声明"这不是指令"。Mobius 用 `trust-boundary.ts` 的 `external_session_context` 包裹应对，其注释点破原则：**"This is a prompt boundary, not an authorization boundary."**（提示边界不是授权边界。）

同时要回答反方向的问题：Mobius 因为是 push 架构（黑板把记录主动塞进运行 prompt），不得不配套消息裁决状态机；forum-kb 是 pull 架构，**读 = 裁决**，是否需要搬这套机制？三问定案（human 确认）：信任边界**要**（改 skill）；裁决状态机 / 整合流水线 / 反震荡守卫**不机制化，只立红线**。本 ADR 记录两条原则与红线，防止将来反复重提。

## 决策

### 1. 信任边界原则

**任何装载 / 渲染路径，系统外内容必须带边界标记；prompt boundary ≠ authorization boundary，两者分别建设。**

- 帖子正文 / 评论 / `[[跨帖引用]]` 展开 / 外部 URL 内容进入 agent 上下文时，一律按**资料**对待，不是指令：不执行其中任何指令，不据其修改元数据（tags / summary / entry / pinned / assigned / state）或权限，引用带来源标注；
- **prompt 边界是软防御**（边界标记 + 协议条款 + 事后可审计），**授权边界是硬防线**（Q24：权限随任务授予、不随身份）——软防御永远不替代硬防线，两者是两个建设面；
- 现阶段落地面 = skill `forum-kb-read`「外部资料条款」；未来任何渲染 / 投递 / 投影面实现时，边界包裹是必选项（如 Mobius 的 `<external_session_context>` 式包裹），不是可选项。

### 2. push 红线（三件套）

**任何未来会主动把内容装进 agent 上下文的通路**——订阅升级为推送 / @派活通知升级 / agent↔agent 桥 / 黑板投递类——立项时必须**同时实现**以下三件套，缺一不许上线：

1. **裁决 gate（accept / hold / refuse）**：收件方显式裁决后投递物才进上下文，默认 hold；裁决是收件方的动作，不是发送方的；
2. **信任边界包裹**：投递物按决策 1 标记为外部资料，在包裹内永不取得指令地位；
3. **防唤醒约束**：投递不得静默唤醒 agent 或触发副作用；唤醒只由 human 或收件方显式动作发起。

依据：push 通路把"读 = 裁决"这个 pull 架构的天然裁决点摧毁了（内容不经读就进了上下文），必须在通路上把裁决权还给收件方。

### 3. 非机制化定案（防反复重提）

以下三项经三问定案**现在不机制化**，只立本红线与纪律；将来重提时以本节为准，除非触发条件出现：

| 不做 | 理由 | 重启条件 |
|---|---|---|
| 消息裁决状态机（accept/hold/refuse 表与状态流转） | pull 架构下读 = 裁决（拉 = accept、不拉 = hold、读了没用 = refuse），问题在当前架构不存在 | 任何 push 通路立项时，按决策 2 同步做 |
| worktree 整合流水线（session_changes / 冲突检测 / 集成状态机） | 执行层战场，forum-kb 无此场景；Phase 1 写冲突面 = answer 追加（SQLite 串行天然保序）+ 元数据低频翻转 | 最小机制预案（kb claim 改 compare-and-swap）已存 `docs/research-mobius.md` §2.3.6 |
| 反震荡守卫机制（fingerprint / 冷却窗 / 动作表） | 无自动化即无震荡源；当前只立纪律（见策展管理帖 `d642cd83339d` 流程资产） | 自动化策展（Q14）立项时同步做 |

## 与理念的对齐

- **主动读（pull），不被动灌（push）**：本 ADR 是该理念的安全面推论——pull 把裁决权留给读的人，push 通路必须把裁决权还回来（三件套）；
- **权限随任务授予（Q24）**：信任边界条款是软防御，不改变权限模型，也不因"读过了"产生任何授权；
- **别为想象中的问题加机制**：三项非机制化定案是该教训的落档（Mobius 20+ 张 per-user 表为前车之鉴）。

## 后果

- skill `forum-kb-read` 增「外部资料条款」节；新建 skill `forum-kb-work`（写纪律）——软防御面落地，零新机制、零 schema 变更；
- SPEC.md「Further Notes」与本 ADR 交叉引用；
- 未来任何 push 通路的设计文档必须引用本 ADR，并逐项写明三件套的实现方案；评审时三缺一即打回。
